# 编写 PRD 和 SPEC

当用户想要创建 PRD(Product Requirement Document) 或 SPEC(Specification) 时将调用此技能。如果你认为某些步骤不必要，可以跳过。

1. 请用户详细描述他们想要解决的问题以及任何潜在的解决方案想法。
2. 探索仓库以验证他们的主张并了解代码库的当前状态。
3. 持续采访用户的计划各个方面，直到达成共同理解。逐一深入探讨每个设计分支，逐个解决决策之间的依赖关系。
4. 勾勒出完成实现所需构建或修改的主要模块。积极寻找提取可独立测试的深度模块的机会。
    - 深度模块（与浅层模块相对）是指将大量功能封装在简单、可测试且很少变化的接口中的模块。
    - 与用户确认这些模块是否符合他们的期望。与用户确认他们希望为哪些模块编写测试。
5. 一旦你对问题和解决方案有了完整的理解，先使用 PRD 模板编写 PRD。PRD 确认后，再使用 SPEC 模板编写 SPEC。

<prd-template>

## 问题陈述

描述需要解决的功能问题或约束缺失。说明当前状态的不足和带来的风险。

## 解决方案

描述解决该问题的技术方案。说明 PRD 的作用（如行为约束基准、开发参考等）和覆盖范围。

## 用户故事

按照以下格式描述核心用户场景：

- 作为 [角色]，我希望 [功能]，以便 [价值/收益]

用户故事应聚焦用户目标而非具体实现，每个故事可拆解为多个功能清单项。

## 功能清单

功能清单应全面覆盖功能的各个方面，按功能模块合理分类。使用无序列表, 命名规则为 `功能-*`, 每条 1-2 句，描述系统应支持的功能。避免口语化表述，聚焦功能本身而非用户视角。

<function-list-example>

### 功能-选择操作

- 支持全选、反选、单选、范围选择（Shift+点击）
- Ctrl+A 在批量模式下全选

### 功能-筛选与状态

- 筛选条件改变时自动清空选择状态
- 视图模式切换时保留选择状态

</function-list-example>

## 行为约束矩阵

定义关键场景的预期行为，确保重构前后一致性。每个场景应包含：

| 场景 | 触发条件 | 前置状态 | 预期行为 | 预期结果状态 |
|------|----------|----------|----------|-------------|

- 场景应覆盖主要功能路径和边界情况
- 预期行为描述"做什么"而非"怎么做"
- 预期结果状态描述操作后的系统状态

## 状态流转

描述系统的核心状态和状态转换条件。适用于有明确状态机的功能：

- 列出所有可能的状态
- 列出每个状态之间的转换条件和触发器
- 标注不可逆转换（如删除后无法恢复）

## 超出范围

描述本 PRD 范围之外的内容。

## 约束检查清单

重构完成后必须逐项核对的检查清单。格式：

- [ ] 检查项 1
- [ ] 检查项 2

应覆盖：

- 功能清单中每项功能是否正常工作
- 行为约束矩阵中每个场景是否符合预期
- 状态流转是否正确
- 事件名称和 payload 是否一致

## PRD 进一步说明

关于此功能的任何其他说明。

</prd-template>

<spec-template>

## 实现决策

已做出的实现决策列表。可以包括：

- 将要构建/修改的模块
- 将要修改的模块接口
- 开发人员的技术澄清
- 架构决策
- 模式变更
- API 契约
- 具体交互

不要包含具体的文件路径或代码片段。它们可能很快就会过时。

## 模块设计

描述主要模块的职责划分和接口设计：

- 模块职责
- 公开接口
- 依赖关系
- 数据流

## 测试决策

已做出的测试决策列表。包括：

- 什么是好测试的描述（只测试外部行为，不测试实现细节）
- 哪些模块将被测试
- 测试的先例（即代码库中类似的测试类型）

## SPEC 进一步说明

关于此功能的任何其他说明。

</spec-template>
