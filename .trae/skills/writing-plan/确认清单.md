# 确认清单

## 子需求确认规则

- 每次请求用户确认某个子需求时，必须提供至少 3 个选项，最多 5 个选项
- 允许联想 web search 和想象 dream，用于扩展可选方案与比较维度
- 选项必须互斥、可执行、便于用户直接选择，不得只给开放式追问
- 必须明确给出推荐项
- 必须同时给出推荐理由，说明为什么该选项更适合当前任务、成本、风险或后续维护
- 若没有足够信息构造 3 个有效选项，说明阶段 0 仍未澄清到位，应继续追问补齐信息，而不是跳过该规则

## 工程化设计清单

- 每个已确认的需求项都应至少对应3个设计选项，且必须给出推荐项和推荐理由

## 类型与框架

- 明确使用的编程语言、框架、库和工具链，说明选择理由与替代方案
- 明确使用的架构风格（如微服务、单体、事件驱动等）和设计原则（如 SOLID、DRY、KISS 等），说明选择理由与替代方案
- 明确使用的设计模式（如工厂、代理、单例、策略、模板方法、适配器等），说明选择理由与替代方案
- 明确使用的数据库类型（如关系型、文档型、时序型等）和具体产品，说明选择理由与替代方案
- 明确使用的缓存方案（如本地缓存、分布式缓存等）和具体产品，说明选择理由与替代方案
- 明确使用的 RPC / typed API 框架和协议，说明选择理由与替代方案
- 明确使用的日志、指标、追踪和监控方案，说明选择理由与替代方案
- 明确使用的部署方案和运维工具，说明选择理由与替代方案
- 明确使用的测试框架和测试类型（如单元测试、集成测试、端到端测试等），说明选择理由与替代方案
- 明确使用的性能优化方案和工具，说明选择理由与替代方案
- 明确使用的安全方案和工具，说明选择理由与替代方案
- 明确使用的其他相关技术方案和工具，说明选择理由与替代方案
