## [LRN-20260328-001] best_practice

**记录时间**: 2026-03-28T10:35:00+08:00
**优先级**: high
**状态**: applied
**领域**: backend

### 摘要
导入导出功能的设计原则和实现经验

### 详情
本次导入导出功能重构涉及多个方面，总结出以下最佳实践：

#### 1. 数据备份策略
- **不导出可再生的数据**：缩略图可以从原图重新生成，不应备份
- **不导出环境相关配置**：字体、设置等可能因环境而异，不应强制恢复
- **使用数据版本号**：用 `dataVersion` 替代 `appVersion` 进行兼容性检查，避免应用版本差异导致的问题

#### 2. 时间格式选择
- 使用本地时间格式（YYYY/M/D H:mm:ss）而非 ISO 格式，更符合用户阅读习惯
- 导出和导入使用统一的时间工具函数 `localTime()`

#### 3. 进度报告设计
- 进度百分比应该连续，避免跳跃
- 每个阶段的状态和详情应该清晰明确
- 完成时需要用户确认，不要自动关闭对话框

#### 4. 资源生命周期管理
- 文件系统操作前确保相关资源已释放（如关闭数据库连接）
- 异步操作必须使用 Promise/async-await 正确处理
- 资源状态变更后需要重新初始化（如恢复数据库后重新连接）

#### 5. 错误处理和回滚
- 关键操作（如导入）需要提供回滚机制
- 回滚操作本身也可能失败，需要考虑双重失败的情况
- 错误信息应该清晰，告知用户已自动回滚

#### 6. 类型定义维护
- 修改数据结构时同步更新 TypeScript 类型定义
- 使用 JSDoc 注释说明字段用途
- 移除不再使用的字段，保持接口简洁

### 建议操作
- 设计备份功能时，先明确哪些数据需要备份、哪些可以再生
- 涉及文件锁定的操作（数据库、日志文件等），必须确保资源已释放
- 进度报告应该考虑用户体验，避免长时间无反馈
- 关键操作提供回滚机制，并测试回滚逻辑

## [LRN-20260402-001] best_practice

**记录时间**: 2026-04-02T14:30:00+08:00
**优先级**: high
**状态**: applied
**领域**: tests

### 摘要
E2E 测试防重复提交功能的最佳实践

### 详情
本次编写新建提示词防重复提交 E2E 测试，总结出以下经验：

#### 1. Playwright 点击行为特性
- Playwright 的 `locator.click()` 会等待元素稳定（visible, enabled and stable）
- 当测试防重复提交功能时，第一次点击后按钮可能被禁用或页面关闭
- 后续点击会因为元素不稳定而失败或超时

#### 2. 测试防重复提交的正确方法
- 使用 `page.evaluate()` 在浏览器端直接触发点击事件
- 这样可以绕过 Playwright 的稳定性检查，模拟真实的快速点击
- 示例代码：
  ```typescript
  await page.evaluate(() => {
    const btn = document.getElementById('doneBtn');
    for (let i = 0; i < 5; i++) btn?.click();
  });
  ```

#### 3. 验证策略
- 不要依赖中间状态的截图（因为操作很快）
- 通过 API 验证最终状态（如数据库记录数）
- 验证只创建了一条记录，而不是验证点击过程中的提示信息

#### 4. E2E 测试规范要点
- 每个关键操作后截图（使用 `test-results/` 目录）
- 使用 `waitForSelector` 和 `waitForFunction` 验证页面状态
- 不要假设页面状态，必须显式验证
- 设置合理的超时时间（简单操作 1000ms，保存操作 3000ms）

#### 5. 测试用例设计
- 正常场景：快速点击多次，验证只创建一条记录
- 边界场景：空内容提交，验证不创建记录
- 压力场景：更多次的快速点击，验证系统稳定性

### 建议操作
- 测试防重复提交/防抖功能时，使用 `page.evaluate()` 触发快速操作
- 验证最终状态而非中间过程
- 通过 API 查询数据库状态，而不是仅验证 UI
- 更新 E2E 测试 SKILL.md，记录这些最佳实践
