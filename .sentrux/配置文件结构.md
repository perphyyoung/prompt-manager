# Sentrux 配置文件结构

Sentrux 通过 `.sentrux/rules.toml` 配置架构规则约束，所有配置项均为可选，只有设置的约束才会被检查。

---

## `[constraints]` - 约束条件

### 1. 根本原因门限（Root Cause Gates）

这些是质量维度的最小分数要求（范围 0.0-1.0）：

| 配置项 | 类型 | 默认值 | 含义 |
|--------|------|--------|------|
| `min_quality` | `f64` | - | 质量信号（Quality Signal）最小值（5个根本原因维度的几何平均值） |
| `min_modularity` | `f64` | - | 模块化（Modularity）分数最小值（归一化的 Newman's Q 算法） |
| `min_acyclicity` | `f64` | - | 无环性（Acyclicity）分数最小值（1.0 = 无循环依赖，0 = 完全循环） |
| `min_depth` | `f64` | - | 深度（Depth）分数最小值（1.0 = 浅层架构，0 = 深层嵌套） |
| `min_equality` | `f64` | - | 均衡性（Equality）分数最小值（1.0 = 复杂度均匀分布） |
| `min_redundancy` | `f64` | - | 冗余度（Redundancy）分数最小值（1.0 = 无死代码/重复代码） |

### 2. 工程限制（Engineering Limits）

| 配置项 | 类型 | 默认值 | 含义 |
|--------|------|--------|------|
| `max_coupling_score` | `f64` | - | 最大耦合度（Coupling）分数（如 0.35，值越小耦合越松） |
| `max_cycles` | `usize` | - | 最大允许循环依赖（Circular Dependency）数量 |
| `max_cc` | `u32` | - | 单函数最大圈复杂度（Cyclomatic Complexity，衡量函数分支数量） |
| `max_file_lines` | `u32` | - | 单文件最大行数 |
| `max_fn_lines` | `u32` | - | 单函数最大行数 |
| `no_god_files` | `bool` | `false` | 是否禁止上帝文件（God File，指扇出 Fan-out > 15 的文件，即依赖过多其他模块的文件） |
| `max_upward_violations` | `usize` | - | 最大允许向上依赖（Upward Dependency）违规数量 |

## Fan-in 与 Fan-out 对比说明

在软件架构中，Fan-in 和 Fan-out 是衡量模块耦合度的关键指标：

| 指标 | 英文术语 | 定义 | 计算公式 | 含义 |
|------|----------|------|----------|------|
| **Fan-out** | Efferent Coupling (Ce) | 该文件**导入/依赖**了多少其他模块 | 该文件的 import 数量 | 衡量文件的**对外依赖**程度 |
| **Fan-in** | Afferent Coupling (Ca) | 有多少其他模块**导入/依赖**该文件 | 导入该文件的文件数量 | 衡量文件的**被依赖**程度 |

### 实际示例

假设有以下代码结构：

```typescript
// constants.ts - 纯常量定义文件
export const MAX_SIZE = 100;
export const API_URL = "https://api.example.com";
// 该文件的 Fan-out 很低（几乎不导入其他模块）
// 该文件的 Fan-in 可能很高（被很多文件导入）

// user-service.ts - 业务逻辑文件
import { MAX_SIZE, API_URL } from './constants';
import { HttpClient } from './http';
import { Logger } from './logger';
// 该文件的 Fan-out 较高（导入了 3 个模块）
// 该文件的 Fan-in 取决于有多少文件使用它
```

### Sentrux 中的应用

| 检测类型 | 使用的指标 | 阈值 | 含义 |
|----------|-----------|------|------|
| **God File** | Fan-out | > 15 | 文件依赖过多其他模块，过于复杂 |
| **Hotspot** | Fan-in + Instability | Fan-in > 20 且 Instability >= 0.15 | 被大量依赖且不稳定的文件 |

### 关键区别

- **God File**：关注"**依赖太多**"（Fan-out 高）
- **热点文件（Hotspot）**：关注"**被太多依赖且不稳定**"（Fan-in 高 + 不稳定性高）

一个纯常量文件（如 `constants.ts`）即使被 38 个文件导入（高 Fan-in），只要它的 Fan-out 很低，就**不会**被判定为 God File。

## `[language.<name>.constraints]` - 语言特定约束

支持按语言覆盖全局约束，优先级高于全局配置：

```toml
[constraints]
max_cc = 20              # 全局默认

[language.python.constraints]
max_cc = 10              # Python 更严格

[language.rust.constraints]
max_cc = 25              # Rust 更宽松（match 分支较多）
```

---

## `[[layers]]` - 分层架构定义

定义代码的分层结构，用于强制依赖方向。

| 字段 | 类型 | 必填 | 含义 |
|------|------|------|------|
| `name` | `string` | 是 | 层名称（如 "core", "app", "ui"） |
| `paths` | `array[string]` | 是 | 匹配该层的 glob 模式列表 |
| `order` | `u32` | 否 | 层顺序（未指定时按数组位置） |

### 分层规则

**核心原则**：`order` 值越小 = 越基础/核心层；`order` 值越大 = 越上层/外围层

```toml
[[layers]]
name = "core"
paths = ["src/core/*"]
order = 0          # 最底层，核心基础设施

[[layers]]
name = "app"
paths = ["src/app/*"]
order = 1          # 中间层，业务逻辑

[[layers]]
name = "ui"
paths = ["src/ui/*"]
order = 2          # 最上层，展示层
```

**依赖方向规则**：

- ✅ **允许**：高 order 层依赖低 order 层（上层依赖下层）
- ❌ **禁止**：低 order 层依赖高 order 层（底层不能依赖上层）

**违规判定**：当 `from_ord < to_ord` 时触发违规。

## `[[boundaries]]` - 边界规则

定义模块间的显式访问限制（禁止某些导入关系）。

| 字段 | 类型 | 必填 | 含义 |
|------|------|------|------|
| `from` | `string` | 是 | 源文件的 glob 模式 |
| `to` | `string` | 是 | 目标文件的 glob 模式 |
| `reason` | `string` | 否 | 规则的人类可读原因 |

```toml
[[boundaries]]
from = "src/ui/*"
to = "src/core/internal/*"
reason = "UI 层不能直接依赖核心内部模块"

[[boundaries]]
from = "src/utils/*"
to = "src/features/*"
reason = "工具模块应独立于业务功能"
```

**含义**：匹配 `from` 模式的文件**不能**导入匹配 `to` 模式的文件。

## Glob 模式支持（Glob Pattern）

Glob 是一种文件路径匹配模式（类似正则表达式但更简单），Sentrux 支持以下模式：

| 模式 | 匹配示例 |
|------|----------|
| `dir/*` | `dir/file.ts`（仅直接子文件，不递归） |
| `dir/**/*` | `dir/a/b/c/file.ts`（递归匹配任意深度的文件） |
| `dir/**` | `dir/a/b/c/file.ts`（同 `/**/*`，递归匹配） |
| `*.ext` | `any/file.ext`（任意位置的特定扩展名文件） |
| `prefix` | `prefix/path/file.ts`（前缀匹配，以指定路径开头） |

## 完整示例配置

```toml
[constraints]
# 根本原因门限
min_quality = 0.7
min_modularity = 0.6
min_acyclicity = 0.9

# 工程限制
max_coupling_score = 0.35
max_cycles = 0
max_cc = 25
max_file_lines = 500
max_fn_lines = 50
no_god_files = true

# 语言特定覆盖
[language.python.constraints]
max_cc = 15

# 分层定义
[[layers]]
name = "core"
paths = ["src/core/*"]
order = 0

[[layers]]
name = "analysis"
paths = ["src/analysis/*"]
order = 1

[[layers]]
name = "app"
paths = ["src/app/*"]
order = 2

[[layers]]
name = "e2e"
paths = ["e2e/**/*"]
order = 3

# 边界规则
[[boundaries]]
from = "src/app/*"
to = "src/core/internal/*"
reason = "App 层不能依赖核心内部模块"
```

## 检查规则生效条件

| 规则 | 生效条件 |
|------|----------|
| 根本原因门限 | 对应的 `min_*` 配置存在 |
| 工程限制 | 对应的 `max_*` 配置存在或 `no_god_files = true` |
| 分层检查 | `[[layers]]` 定义数量 >= 2 |
| 边界检查 | `[[boundaries]]` 定义存在 |

运行 `sentrux check .` 会检查所有已配置的规则，退出码 0 表示全部通过，1 表示存在违规。
