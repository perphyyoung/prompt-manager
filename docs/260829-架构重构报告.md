# 架构重构报告

> 项目:prompt-manager(Electron 桌面应用 · 本地提示词管理工具)
> 分支:`refactor/architecture`(基于 `d1f48ff8`,共 10 个提交)
> 方法:整洁架构 lite(六边形)× 功能垂直切片,全程 gitnexus 图谱分析 + 分层验证

---

## 一、概述

本次重构将一个"三层核心文件各自成为上帝模块、分层名存实亡"的 Electron 应用,改造为**依赖方向单向、由 lint 护栏锁定、IPC 面单一契约约束**的模块化架构。

三个核心文件的变化:

| 重构前 | 重构后 |
|---|---|
| `main/index.ts` 2407 行:92 个 IPC handler + 窗口/托盘/生命周期 + 文件系统 + 备份 + 构建/重启 | 11 行纯入口 + `bootstrap.ts`(装配)+ 6 个按域 IPC 路由 + `runtime.ts` + 3 个基础设施模块 |
| `main/database.ts` 3579 行:约 90 个函数平铺,连接/迁移/事务与全部领域 SQL 交织 | 95 行 facade + `sqlite/connection.ts`(574)+ 5 个按域 repository(image/prompt/tag/tagGroup/stats)|
| 无契约:92 个通道名在 main 与 preload 两边手写字符串,`as` 断言绕过完整性检查 | `shared/ipc-contract.ts`(336 行):86 通道 + 2 推送事件 + 全通道签名 + 编译期完备性断言,双端 `handleTyped`/`bridge` 接线 |

---

## 二、重构前的问题诊断

诊断基于 gitnexus 索引+ 实际代码阅读,问题按严重度排序:

1. **`main/index.ts` 上帝模块**:92 个 `ipcMain.handle` 注册与窗口管理、缩略图生成、备份压缩、甚至 `runBuild` 混在一个文件,接口适配/业务用例/基础设施三层职责不可区分。
2. **`database.ts` 上帝 DAO**:3579 行单命名空间,sqlite 连接池、事务、错误解析与 prompts/images/tags/trash/stats 全部领域 SQL 交织;模块级单例 `db` 无法注入,主进程业务不可单测。
3. **renderer 服务定位器**:`App` 类 new 出约 20 个 Manager 后把自身(`this as IApp`)塞给每一个;`IApp` 接口暴露 20+ Manager 字段,任何 Manager 能伸手拿任何其他 Manager;`this.app.X` 共约 380 次访问,其中两个 PanelManager 的跨 Manager 伸手占 64 次。
4. **`src/middle` 假分层**:`BatchToolbarMiddle`(923 行)做 DOM 操作、调 renderer 的 DialogService,却被放在 src 根目录;与 renderer 形成**双向 import**(文件级唯一的真循环倾向)。
5. **IPC 面无契约**:通道名字符串两处手写;preload 实现对象用 `as IElectronAPI` 断言(缺方法不报错)。
6. **双胞胎实体靠字符串复制**:`DataType = 'prompt' | 'image'` 参数散落各处,配合平行配置表复制业务逻辑。
7. **两套领域模型互相撒谎**:main 的 `Prompt/Image`(database-types)与 renderer 的 `IPrompt/IImage`(entities)结构不等价——`isFavorite` 一边 boolean 一边 number、`thumbnailPath/width/height/deletedAt` 的 null 未声明。
8. **命名与位置噪音**:`pyTagGroups`/`pyBatchToolbar`(历史遗留 "py" 前缀)、`src/middle`、652 行的 `constants.ts` 被 main/renderer/lib 四方引用。

**基线中的优点**(重构予以保留):文件级零循环依赖;preload 边界干净;`DataClearApi` 已是标准端口-适配器写法;`pyTagGroups` 是有独立测试的纯逻辑库。

## 三、方案选型

**为什么不是完整 DDD**:DDD(聚合根/值对象/领域事件/防腐层)的价值前提是业务规则复杂多变。本项目的现实是两条以 UI 为中心的垂直切片(Prompt/Image),复杂度集中在交互而非领域;全套 DDD 对单人维护的 CRUD 应用是负资产。

**采用的组合**:

- **整洁架构 lite(六边形)**:只强制一条硬规则——依赖方向单向 `interfaces(IPC/View) → application → domain ← infrastructure`,domain 不依赖任何外层;
- **端口-适配器**:把项目里已有的最佳实践(`DataClearApi` 接口 + Electron/Mock 双实现)推广为全局模式;
- **DDD 战术补丁**:标签操作作为领域服务保留 `lib/tag-groups`;Prompt/Image 通过共享的领域概念收敛,而非合并代码;
- **垂直切片**:renderer 按 feature 组织,`src/middle` 归位为 `renderer/features/batch-toolbar`。

## 四、分阶段实施

### 阶段 1|拆分 main/index.ts(commit `bbbef546`,纯搬运)

- 入口缩为 11 行:`registerAllIpc()` + `startApp()`;
- `bootstrap.ts`:窗口/托盘/生命周期/单实例锁;

### 阶段 2|拆分 database.ts(commit `1fc5e92f`,脚本逐字节搬运)

- 手写切分脚本按行范围搬运 + 自动扫描各模块实际用到的标识符生成 import;`database.ts` 变 95 行 facade;
- 产物:`infrastructure/sqlite/connection.ts`(连接/事务/迁移/PRAGMA/run-get-all/getDb 访问器)+ 5 个按域 repository(image/prompt/tag/tagGroup/stats)。

### 阶段 3-4|类型归位 + 杀掉 middle(commit `b694ab9a`)

- `database-types.ts`(零依赖纯类型)迁至 `src/shared/domain/`,消除 renderer→main、preload→main 的类型引用(10 个文件);
- 删除 `src/middle`,`BatchToolbarMiddle` 迁入 `renderer/features/batch-toolbar/`,其对 renderer 的反向 import 改为构造注入——**唯一的文件级双向依赖消除**;
- gitnexus 图谱复核:renderer→main 边 = 0,middle 相关边 = 0。

### 阶段 5a|库归位 + 分层护栏(commit `dbdf4c3b`)

- `pyTagGroups → src/lib/tag-groups`、`pyBatchToolbar → src/lib/batch-toolbar`,tests 目录同步更名;
- `.oxlintrc.json` 新增三条 `no-restricted-imports` 护栏:
  - renderer/preload 禁止引用 main;
  - shared 层零依赖(仅允许 `../types` 纯类型目录);
  - main/interfaces 禁止引用 renderer。
- **阶段 1-4 的成果从此由 lint 强制,不靠自觉**。

### 阶段 5c|renderer 依赖注入三步走(commits `803a8392` / `7b7a5e7a` / `c87d4cc7`)

第一步,**依赖显式化**:扫描每个 Manager 函数体对 `this.app.X` 的真实访问,生成 `Pick<IApp, ...>` 窄类型;17 个 Manager 的 `app` 字段全部收窄;顺带消灭 6 个文件各自复制的本地 `interface IApp` 存根、`HoverTooltipManager` 的死 app 参数、2 处历史遗留 cast。**函数体零改动,typecheck 充当完整性校验器**。

第二步,**升级为独立 port**:11 个 `Pick` 展开为独立接口(56 个成员声明,脚本从 IApp 定义逐字解析,类型零漂移)。`IApp` 从此只存在于 app.ts(App 类实现)与定义处——Manager 层彻底不认识上帝接口,任何 Manager 可脱离 App 独立构造与单测。

第三步,**TagManager 家族收尾**:`app: any` 实测依赖仅 3 成员(showToast 22 处 + 两个 panel 引用),收窄为 `TagManagerDeps`。renderer 内不再有任何 `app: any`。

### 阶段 5d|constants 按层归位(commit `43e4edcf`)

- `constants.ts`(652 行)→ `renderer/constants.ts`(ElementId/ICONS/Events 等 UI 常量归属渲染进程);
- `TrashType` 提取至 `shared/domain/trashType.ts`(主进程打标记、渲染进程消费的共享领域常量);
- **至此 src 根目录只剩 main/preload/renderer/shared/lib 五个顶层目录,无游离文件**。

### 阶段 6|IPC 契约(commit `b7440118`,用户决策"加 contract")

- `shared/ipc-contract.ts`:`IPC` 通道名常量 + `IPC_EVENTS` 推送事件 + `IpcApi` 全通道签名 + 编译期完备性断言(漏签名直接报错);
- main 侧 `handleTyped(key, handler)` 替代字符串注册,handler 入参获得真实类型;preload 侧 `bridge(key)` 单行桥接,`as IElectronAPI` 改为 `satisfies`(缺方法/错参数现在会报错);
- 渲染进程零改动(`window.electronAPI` 形状不变)。

### 收尾|死通道删除 + 类型统一(commit `a82729f2`,用户决策)

- 删除 6 个死通道(见下文"契约暴露的问题"),连带删除仓库层死函数 `isTitleExists`/`getPromptImages`/`optimizeDatabase`;
- 类型统一:以主进程实际为线格式真相,修正 renderer 侧声明(详见下文),移除 main 侧 9 处返回方向边界 cast;
- 保留 3 处命令方向适配(addPrompt/updatePrompt/updateImage 的 `Create/Update*Params`)——命令类型与实体类型的差异是合理建模,不是债。

## 五、契约的第一手收益:暴露的真实问题

"加不加 contract"的争论用实施结果回答——**契约第一次编译就抓出 20 多处人肉对齐时代的漂移**:

**签名漂移(已修复)**

| 问题 | 修复 |
|---|---|
| 18 个通道 preload 声明返回 `void`,main 实际返回 `boolean`/`string[]`(软删除、恢复、清空回收站、加标签返回最新列表等) | 契约以 main 实际为准 |
| `rebuildThumbnails` 空库分支返回缺 `failed` 字段,而声明说必有 | main 补齐 |
| `selectAndInstallFont` 声明 `{success,...}` 包装形状,main 实际直接返回 `{fontName,fileName,filePath}` | 取 main 实际(已核实 renderer 解构用法无冲突) |
| `getAllTags` 的 null 分支实际不可达(initTagsCache 失败也兜底 `[]`) | 契约收紧 |
| `addPrompt` 语义:title 缺省时 main 以 id 兜底,失败返回 null——声明均未体现 | 契约诚实化 |

**死代码(已删除,经用户决策)**:6 个 main 有 handler 但 preload 从未桥接的通道——运行时不可达,纯维护负担。

**类型谎言(已核实非活 bug,已统一)**:`isFavorite` 双端 number/boolean 不一致——renderer 全部用真值判断(`!!x`)消费,无 `=== 1` 比较,故从未炸过;但 4 处真的在写 `1/0`。统一为 boolean 并同步全部写入点。

**保留的类型债(显式标记)**:3 处命令方向的参数适配(`Partial<IPrompt>` → `UpdatePromptParams` 等),命令类型与实体类型差异是合理建模,非谎言。

## 八、关键决策记录

1. **database.ts 拆分用 facade 过渡**:facade 保持导出面不变,92 个调用方零改动——把"搬代码"与"改调用方"解耦,风险减半。未来调用方可逐个改为直接 import repository,再撤 facade。
2. **端口演进三步走**:先 `Pick<IApp,...>`(显式化)→ 再独立接口(解耦)→ 不强求一次性构造注入。每步 typecheck 仲裁、函数体零改动,风险恒定在最低档。
3. **契约以 main 实际为准,而非 preload 历史声明**:18 个通道的返回类型按 main 修正——preload 的声明是"渲染进程希望的样子",契约必须描述"线上真实发生的事"。
4. **实体统一方向**:以 main 领域模型为线格式真相,renderer 类型向其对齐;`interface → type 别名`是关键一步(interface 无隐式索引签名导致跨家族永不可赋值,这也是边界 cast 存在的根因)。
5. **保留 3 处命令方向参数适配**:命令类型与实体类型的差异是合理建模,不视为债。

## 附录 A|四层与目录的映射,及顶级目录改名方案

第三章的依赖规则 `interfaces(IPC/View) → application → domain ← infrastructure` 描述的是**依赖方向**,不是目录规划。它与目录是"多对多带模糊"的映射,因为**进程边界(main/preload/renderer)与层次边界(四层)是正交的两个维度**:前者由 electron-vite 构建、contextIsolation 安全模型物理强制,是第一等边界;四层是每个进程内部的第二等组织。

### A.1 四层 ↔ 当前目录对照

| 四层 | 当前目录 | 说明 |
|---|---|---|
| **interfaces**(接口适配) | `main/interfaces/ipc/`(6 路由)、`preload/`(安全桥)、`renderer` 的 `managers/ features/ components/ configs/` | UI 本身就是整洁架构里的驱动适配器 |
| **application**(用例) | **无独立目录**。main 侧 handler 目前是薄透传;`renderer/services/`(TagService、ImageUploadService、DataClearApi)承担了用例职责;`backupIpc` 的导入/导出备份是内联的大用例 | 四层中唯一缺位的 |
| **domain**(领域) | `shared/domain/`(database-types、trashType)、`lib/tag-groups/`(标签规则 + 独立测试)、`types/entities.ts`(线格式视图,与 domain 同族) | 全部零依赖 |
| **infrastructure**(基础设施) | `main/infrastructure/`(sqlite 连接 + 5 仓库 + imageFiles/tagCache/backup)、`main/database.ts`(facade 门面)、`utils/CacheManager`、`renderer_utils/` 技术件 | |

四处归属模糊(如实说明):`bootstrap.ts` + `index.ts` 是**组合根/进程入口**,不属于任何一层;`preload/` 是跨层的纯适配器进程;`utils/` 是共享工具箱;`lib/batch-toolbar` 是 UI 配置库,偏 interfaces 侧的配置。

### A.2 方案 A(推荐):顶级目录不动,application 按需生长

1. 顶级维持 `main / preload / renderer / shared / lib / types / utils` 不变;
2. main 内已具备 `interfaces/` 与 `infrastructure/`;**当 handler 里长出跨仓储编排逻辑时新增 `main/application/`**(如把导入备份从 `backupIpc` 提为 `application/backupService.ts`);
3. `renderer/services/` 即 application 雏形,不强制改名;
4. 分层护栏维持现有 3 条。

成本:仅本附录的文档;零代码改动。

### A.3 方案 B(完整改造):顶级目录改为四层 + 进程子目录

```
src/
```

### A.4 结论

推荐方案 A。**切换到方案 B 的触发条件**:main 侧 application 层真实长出(≥3 个用例服务)、且团队希望用目录名强制 DDD 词汇时再做——届时有真实内容支撑目录,改名的收益才大于成本。
